# Fyne desktop migration and resource plan

Status: in progress. Loops 24–26 passed. Loop 27 has Windows native acceptance and Windows/Linux hosted checks, while Linux visible interaction and macOS native window operation remain open. ADR-020 and ADR-021 are the decision records. This plan replaces the forward-looking Wails/Svelte/NSIS UI and release path; it does not rewrite the historical Loop 01–23 or RA-01–06 evidence.

## Outcome and sequence

The release UI is Fyne with Go core/adapters, no WebView or browser-backed fallback, and no installer. Windows is the current delivery platform. After the complete Windows product is stable, develop and accept Linux; after Linux is stable, develop and accept macOS. Each platform's artifact runs from an extracted folder. MPV remains an external, user-installed player. All six sections and their content work by mouse and keyboard, with visible focus; desktop screen-reader support is not a current release requirement. Existing security, cancellation, error, persistence and playback behavior must remain intact.

Loop 23 and the retrospective baseline are already PASS. No further standalone RA batch is scheduled. RA findings and legacy-boundary risks that need native revalidation become migration acceptance work, not a second retrospective audit. Loop 24 starts the migration; Windows feature work resumes after the Windows-scoped Loop 28 migration gate passes.

The owner clarified that the entire Windows product comes first, including feature Loops 29–42. Linux development follows only when Windows is stable; macOS development follows only when Linux is stable. Loops 27 and 28 now close against Windows-native criteria and explicitly carry Linux/macOS criteria into later platform phases. A Windows-only candidate may be proposed for `main` after those Windows gates pass, with support labeled Windows only. Existing Linux/macOS builds and test results are useful diagnostics but do not imply native platform acceptance. No Windows security, UI, MPV, resource or regression criterion is reduced. The owner authorized the Windows long-idle resource measurement on 2026-09-24. Merging to `main` remains a separately reviewable remote action.

If a slice cannot preserve parity, its next slice does not start. After Windows Loop 28 PASS, Loop 29 resumes Phase 23 Search UI on Windows, then Phases 24–36 map to Loops 30–42 respectively; these are Fyne feature/completion phases, not Svelte work. Loop 29 builds the first deferred Fyne feature screen and must verify its own phase criterion. Linux development begins after the complete Windows product is stable; macOS development begins after Linux is stable. Each later platform needs its own native runtime, keyboard/mouse, portability, resource and human acceptance before being called supported.

## RA-to-migration verification map

Historical RA-01–06 are closed as `LEGACY_VERIFIED` at `3e15651e`. This status is not revoked. Migration revalidates changed boundaries: RA-06's desktop action/DTO, errors, six-section navigation, focus and former CSP trust-boundary tests become native UI and no-WebView checks in M1–M4; RA-03's MPV process, IPC, proxy, cancellation, switching and cleanup become M2/M4 integration gates; RA-04's SQLite lifecycle and state-location behavior become M3 portability/import gates; RA-05's metadata/plain-text/cover bounds become M2/M4 UI data gates. RA-01/02 core/source contracts remain regression checks. Wails-specific CSP is removed only when WebView is gone and equivalent native untrusted-input checks pass. The unresolved live MPV IPC timeout is not a PASS claim and needs an actual native platform diagnosis or an explicitly blocked criterion.

## OneAnime reference and resource gate

[OneAnime's source README](https://github.com/Predidit/oneAnime) identifies Flutter, says normal operation does not load WebView, and names media-kit for playback. Its [entry point](https://github.com/Predidit/oneAnime/blob/main/lib/main.dart) initializes MediaKit, window management and storage before launching the UI; its [dependency manifest](https://github.com/Predidit/oneAnime/blob/main/pubspec.yaml) declares media-kit, Hive, Dio, MobX and window-manager dependencies. These are verified architectural choices, not evidence that a particular cache, widget or GC technique produced its low resident result. Its main branch can differ from the owner's portable 1.4.7 binary; inspect a matching release tag before attributing implementation details to that binary. The owner's OneAnime 1.4.7 Windows screenshots show approximately 26.6 MiB private resident after long idle and 300.3 MiB private commit; an earlier view of the same process showed approximately 92.5 MiB resident. Working-set trimming can lower resident memory without releasing committed private memory. OneAnime's embedded player and our external MPV also differ. Do not claim a specific OneAnime optimization or copy GPL-3.0 code without a separate license review.

M0 records a read-only OneAnime source matrix at the tag/commit matching the owner's 1.4.7 binary if identifiable. Inspect startup and background work, list construction, cover decode/cache lifetime, player creation/disposal, storage and portable packaging. For each observed source behavior, record its file/revision, whether a Go/Fyne/external-MPV equivalent is appropriate, and a measurable hypothesis. If the matching revision cannot be identified or accessed, mark the comparison limited to verified main-branch evidence; do not infer the binary's internals. Do not copy GPL-3.0 implementation code.

An additional [main-branch request implementation](https://github.com/Predidit/oneAnime/blob/main/lib/request/request.dart) shows a shared Dio client and background response transformer, which are useful hypotheses for avoiding redundant network setup and foreground parsing. It also sets `badCertificateCallback` to accept every certificate in one proxy path; that is incompatible with this project's TLS/security contract and must not be adopted. No source observation so far proves the cause of OneAnime's 26.6 MiB resident sample.

The owner's additional observation is that OneAnime's resident memory rises from about 26.6 MiB after a long idle to about 48 MiB on window focus, then about 200–250 MiB during playback. Treat “inactive window suspends work and releases UI/player resources” as a hypothesis, not an established implementation fact. Windows can also trim a process working set without releasing its private commit. M0's source matrix must look for focus/visibility/minimize callbacks, timers/refresh cancellation, image/cache disposal and player lifecycle in the matching revision. The Windows resource gate must sample foreground → unfocused → long idle → focus/wake → playback → stop, recording private resident, private commit, CPU, page faults, GPU memory and process tree at each transition. A fall in resident memory with stable commit alone does not prove application-level suspension. The owner approved this long-idle sequence on 2026-09-24 after previously declining it during planning.

The prior Fyne Home-only short-run samples were 172.3, 130.1 and 125.5 MiB private resident, without full production data or MPV. They are a material warning, not a matched long-idle comparison. The owner approved a Windows long-idle Fyne run on 2026-09-24; record its exact conditions before comparing results.

For each release candidate, record build/version, OS/hardware, display scale, window state, profile size, exact local fixture, MPV version/decoder settings, and ambient load. Use release builds and the same visible content on OneAnime where feasible; label unmatched features. Measure cold/warm startup, 10-second settle and 30-second idle, the authorized focus/idle/wake sequence, scroll/search, repeated open/close and episode switches, one fixed 1080p playback clip, stop/cleanup, and at least three runs per condition. Report all runs and median/range. Record private resident, private commit, total process-tree and incremental system memory, CPU/energy, GPU allocation, page faults, startup latency and disk separately. For playback show app-only, MPV-only and combined totals. Never substitute Task Manager's displayed working set for private commit or a single trimmed minimum for sustained cost.

On the owner's Windows reference host, the provisional acceptance targets are **under 100 MiB sustained app-only idle private resident** with representative data and **under 250 MiB combined app-plus-MPV sustained playback private resident** for the fixed clip, with near-zero idle CPU and no monotonic growth across cycles. The 26.6 MiB OneAnime long-idle result is a comparison goal, not an already proven Fyne result or universal bound. Also report commit and GPU cost; meeting resident alone is insufficient if those regress substantially. Before M4 PASS, fix the exact reference conditions and allowable variance with the owner. If Fyne misses the resource envelope after bounded profiling and causal optimization, stop at `NEEDS_HUMAN` with the measured conflict; do not relax targets, silently switch toolkit, or retain WebView.

Prefer bounded visible-item creation, bounded decoded-cover dimensions/cache, explicit release of offscreen UI resources, cache-first reads, no idle polling, bounded concurrent refresh, reuse of clients, and no duplicate media decoding. These are implementation hypotheses to verify with profiling, not claims about OneAnime's internals. Avoid artificial working-set trimming or forced GC as a substitute for reduced sustained allocation/commit, responsiveness and CPU.

If profiling supports a focus-aware low-activity mode, pause only nonessential refresh, animation and offscreen image work when unfocused/minimized; resume on focus without blocking cached UI or duplicating requests. Do not interrupt external MPV playback, progress checkpoints, security cleanup or user-requested operations merely because the main window loses focus. Validate wake latency and CPU/commit as well as resident memory before retaining this policy.

## Portability and final removal

Windows M3 must specify an extracted-folder data directory, read-only/permission failure behavior, and an explicit opt-in import or copy from the existing `os.UserConfigDir` profile. Never delete or silently move the old profile. Test a fresh folder, upgrade in place, a read-only folder, paths with spaces/non-ASCII characters, and missing external MPV. Document the Linux/macOS runtime library requirements when those platforms enter their own phases; portable means no installer/privileged registration, not a promise of zero system libraries.

The final tree and each platform release must have no Wails/Svelte/NSIS/WebView execution path. Verify source, `go.mod`/lockfiles, build tasks, CI, packaged files, loaded UI libraries and process tree on the platform being accepted. Historical docs and Git may still mention Wails as evidence; that is not a runtime dependency. No production migration, workflow edit, commit, push or release is authorized by this planning document alone.
