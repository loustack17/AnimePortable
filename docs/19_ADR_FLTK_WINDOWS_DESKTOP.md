# ADR-023 — FLTK and in-process libmpv for the Windows desktop

## Status

Accepted for Windows implementation by the owner on 2026-09-25. Supersedes ADR-021 for the Windows desktop implementation. Release, resource and Loop 28 acceptance remain open. Linux follows a stable Windows release; macOS follows stable Linux support.

## Context

The Fyne Windows implementation passed Loop 27 portable and native-interaction checks but missed the Loop 28 idle resource limit: 169.50 MiB private working set after 15 minutes minimized against the under-100 MiB target. The owner requires the complete product to use less resource than OneAnime under comparable conditions. ADR-020 still prohibits WebView, Wails and Svelte as release UI paths.

An isolated Go, FLTK and in-process libmpv Windows prototype has an approved visual direction and working mouse playback, pause, seek, volume, episode selection, fullscreen and stop controls. One 20-second synthetic 720p24 playback run sampled maxima of 167.82 MiB private working set and 568.43 MiB private bytes; four seconds after Stop it sampled 52.99 and 178.45 MiB respectively. Its Home is demonstration content, its clips are local command-line arguments, and it does not use the production service. The short run used different content and conditions from the owner's OneAnime observations and did not measure GPU allocation. It is a feasibility screen, not a completed resource audit or Loop 28 PASS.

## Decision

Replace the Windows Fyne desktop adapter with FLTK and replace external MPV playback with in-process libmpv. Keep the existing Go core, source and metadata adapters, SQLite data, portable `<extracted folder>/data` contract, explicit legacy-data import, and existing security, cancellation, error and playback-lifecycle behavior. Reuse the core `Player`/`PlaybackSession` boundary; do not make widgets responsible for provider validation or persistence policy. Native player controls remain inside the video surface.

The Windows release and Loop 28 PASS require product parity with the currently accepted Fyne slice, equivalent or stronger tests, native keyboard/mouse/focus and portable-artifact checks, exact-state isolated verification, and a matched resource comparison with OneAnime. The unchanged resource objective is whole-product use below OneAnime in comparable idle, wake, playback and cleanup states. Do not infer a pass from the synthetic short run, trim working sets, force GC, weaken security/tests or raise the target to make the result pass.

On 2026-09-26 the owner prioritized replacing the Wails code on `main` before Loop 28 closes. This permits an explicitly marked Windows FLTK development snapshot on `main` after scoped review and exact-commit CI, while release artifacts and Loop 28 PASS remain gated by the requirements above. The snapshot must not bundle the test-only libmpv DLL or claim complete playback portability.

The Windows amd64 default build selects FLTK directly. The owner subsequently paused Linux and macOS development and directed removal of all Fyne, Wails, Svelte, NSIS and external-MPV product paths now. The active source, dependencies and CI are Windows-only; historical documentation and the legacy SQLite `mpv_path` column remain for traceability and old-data compatibility. Later platform work requires new native adapters and their own acceptance evidence.

## Windows replacement gates

1. Production startup: extracted-folder data, first-run new/import choices, failure behavior, close cancellation and portable move/reopen.
2. UI parity: six destinations with the current Home and placeholders, real Library/History/Following data, bounded rows, safe resume Play, loading/error/retry behavior, visible focus, Tab/Shift+Tab, arrows, Enter/Space, mouse and reduced-window scrolling.
3. Player parity: validated source and headers, protected local proxy boundary where needed, progress checkpoints, resume, episode switch, stop and close cleanup, no secret-bearing errors, and no orphan player session.
4. Windows build/package: no Fyne, Wails, Svelte, NSIS or WebView runtime; no installer requirement; actual ZIP extraction and native operation.
   The package must include a versioned, hash-pinned libmpv runtime and its build-specific license notice without committing third-party binaries or source to the repository. Distribution review must resolve mpv and linked codec license terms for that exact build.
   The executable must verify the bundled DLL hash and load it by absolute path only when playback starts; a missing or altered DLL must leave Home available and produce a safe playback error. Reject runtime dependencies outside the package or Windows system directories.
5. Resource comparison: matching content and counters for AnimePortable and OneAnime across comparable Home, idle, refocus, playback and cleanup states, with CPU/GPU and repeatability. The owner must approve a new long-idle run before one is performed.

Loop 29 feature work remains gated by Windows Loop 28 acceptance. Linux and macOS acceptance are separate later phases and are not passed by Windows evidence.

## Windows integration evidence, 2026-09-26

The opt-in production-tag FLTK executable played the existing Loop 23 Anime1 acceptance episode through the real backend, protected local proxy and in-process libmpv. Its 720p player displayed video, episode selection and controls; the stop button returned to Home, and closing Home exited with code 0. Two 12-second host diagnostics measured private working set of 181.07/181.67 MiB and private commit of 609.35/610.31 MiB. One earlier cold sample was 233.41/665.82 MiB. Five seconds after Stop, working set/commit was 56.86/192.48 MiB. A separate 10-second Home run with 200 local anime, 39 following entries and 19 history entries measured 13.28/125.02 MiB. These short, unmatched samples do not establish the OneAnime comparison or long-idle gate.

Independent security review found that the first integration's go-mpv purego backend loaded libmpv by bare DLL name during Go package initialization. This could panic before Home if the DLL was missing and did not prove that the loaded DLL matched the hash-pinned package. A narrow, lazy Windows binding with absolute-path loading and runtime hash verification is required before Windows release; the integration and resource measurements above predate that correction. Two bounded mpv option trials (four software decoder threads and 8 MiB backward cache) gave no material private-commit reduction and were removed.

The replacement now uses a first-party narrow Windows binding. It verifies the adjacent DLL against the pinned SHA-256 and retains a read-only, non-shareable-for-write/delete file handle through `LoadLibraryEx` and symbol binding; the loader limits dependency search to the DLL directory and Windows System32. A focused race test, a native real 720p playback/seek/stop/close run, and native missing/corrupt DLL runs passed. The latter keep Home usable and show an inline playback error. Independent security re-review found no remaining evidenced MUST_FIX in this loader path. The current 12-second playback sample was 181.14 MiB private working set and 612.77 MiB private bytes; five seconds after Stop it was 55.63/181.98 MiB. These remain unmatched host diagnostics. The candidate DLL imports `vulkan-1.dll` from System32 on this host; clean-machine portability and the exact build's license/codec notices remain open.

On 2026-09-26 the Windows amd64 default `go build` and production Taskfile were switched to the FLTK entry. A Windows ZIP request without bundled libmpv fails in the packaging CLI. The owner then directed a Windows-only cleanup: Fyne/native, external MPV IPC, non-Windows build/package source and runtime dependencies were removed. Windows CI now builds and tests FLTK and libmpv without distributing a ZIP. The exact libmpv build's license/codec notices and clean-host runtime dependencies remain unresolved, so a distributable package and Windows Loop 28 PASS remain blocked. Linux and macOS native implementation and acceptance are deferred.

The owner approved a five-minute idle comparison instead of fifteen minutes. In an isolated test profile, AnimePortable with the Loop 23 acceptance data measured 6.26 MiB private resident and 107.18 MiB private commit after five minutes minimized, then 6.27/107.20 MiB thirty seconds after restoring. OneAnime exited before the first 10-second sample when the measurement script launched either a disposable copy or the owner-provided path under profile isolation. The owner then started OneAnime normally, and the script attached read-only to that existing process. After five minutes minimized it measured 98.32 MiB private resident, 309.48 MiB private commit and 59.52 MiB dedicated GPU memory; thirty seconds after restoring it measured 102.64/375.44 MiB and 59.61 MiB dedicated GPU memory. Accumulated process CPU time increased by 0.063 seconds for AnimePortable and 0.078 seconds for OneAnime during their respective five-minute minimized intervals. The script restored and left the owner's OneAnime process running. The Windows GPU process-memory counter had no entry for the idle AnimePortable process. The two apps' Home data, startup age and profile conditions were not matched; AnimePortable also lost foreground focus before its final restored sample. These host observations support a low AnimePortable idle footprint but do not establish a matched resource PASS under `docs/13_VERIFICATION_EXECUTION_ENVIRONMENTS.md`. The owner's earlier 26–46 MiB OneAnime working-set observation did not recur in this five-minute run; its private commit stayed near 309 MiB while minimized.

The owner then found that Enter advanced Home focus instead of activating the selected destination, and some visible episode entries did not play. The first eight Anime1 episode references all resolved through the production source adapter. The next owner check found that directional keyboard focus did not follow the visible controls and Tab wrapped unexpectedly. Owner-visible interaction on the final revision remains pending, so none of these observations closes Loop 28.

## Windows license audit, 2026-09-27

The owner wants AnimePortable's own code to remain MPL-2.0. [Mozilla's MPL FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) confirms that MPL's file-level license can coexist with separately licensed components in a larger work, subject to the applicable distribution conditions. The repository `LICENSE` and own-file SPDX headers remain MPL-2.0; this audit does not change that license. It also does not establish that the combined Windows executable or ZIP may be described as entirely MPL-licensed.

The pinned go-fltk module has an MIT `LICENSE` requiring its copyright and permission notice to be included with copies or substantial portions. `THIRD_PARTY_NOTICES.md` now includes its full MIT notice and lists all Go modules linked into the Windows executable according to `go list -deps`, but does not yet include every linked module's complete license and nested notice text. Its Windows cgo link line statically includes FLTK, JPEG, PNG and zlib archives. The module's local build recipe selects [FLTK 1.4.5](https://github.com/fltk/fltk/releases/tag/release-1.4.5), applies a [Windows patch](https://github.com/pwiecz/go-fltk/blob/3e944122e7b1/lib/fltk-1.4.patch) that disables cleanup calls in `src/Fl_win32.cxx`, and builds with bundled JPEG, PNG and zlib. [FLTK's official exception](https://www.fltk.org/COPYING.php) permits static linking without relicensing the application, but requires modifications to FLTK to be provided under its license. The patch is available in the pinned module; the exact bundled image-library versions/notices and a complete corresponding-source offer still need validation for a distributable ZIP.

The exact pinned OneAnime-derived libmpv DLL remains the release blocker. [mpv's copyright file](https://github.com/mpv-player/mpv/blob/master/Copyright) says mpv is GPLv2+ by default and can be LGPLv2.1+ only when built without GPL-only files; `-Dgpl=false` alone is not a license grant, and linked libraries can change the result. [FFmpeg's legal guidance](https://www.ffmpeg.org/legal.html) says its optional GPL parts make the whole FFmpeg build GPL and calls for matching source and build information when distributing LGPL binaries. The `20260811` release scripts request non-GPL configurations, but the downloaded archive does not supply a complete bill of materials, notices or corresponding source/build record for that DLL. Its LGPL eligibility and distribution obligations therefore remain unverified. Do not publish the pinned DLL or portable ZIP from this evidence.

For Windows Loop 28 release acceptance, obtain a reproducible libmpv build whose component versions, build flags, source availability, licenses and notices are documented; verify the final DLL hash and loaded dependencies; include the required notices and source access with the ZIP. To preserve the owner's MPL-2.0 source-license preference without a GPL-governed combined release, replace any GPL-governed DLL with a verified LGPL-eligible build. Keep AnimePortable's own source under MPL-2.0 and do not relabel a third-party component as MPL.

## Release approach research, 2026-09-27

[oneAnime](https://github.com/Predidit/oneAnime) and [mpv.net](https://github.com/mpvnet-player/mpv.net) distribute their applications under GPL and use libmpv; their licensing does not establish that the same binary can be redistributed as an MPL-only product. [media-kit](https://github.com/media-kit/media-kit) keeps its wrapper under MIT while its [Windows native package](https://github.com/media-kit/media-kit/blob/main/libs/windows/media_kit_libs_windows_video/windows/CMakeLists.txt) downloads a pinned libmpv archive. These are examples of separately identified application and native-component licenses, not proof that our exact DLL has complete distribution metadata. [Jellyfin MPV Shim's packaging notes](https://github.com/jellyfin/jellyfin-mpv-shim/blob/master/docs/packaging.md) demonstrate a concrete native dependency/architecture check for a bundled libmpv release.

[Mozilla's MPL-in-GPL guidelines](https://www.mozilla.org/en-US/MPL/2.0/combining-mpl-and-gpl/) specifically state that an MPL application linking to an LGPL library needs no special relicensing of its own files. A GPL-governed libmpv build is a different route: Mozilla's [MPL FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/) permits an MPL/GPL larger work under Section 3.3, but the combined distribution must satisfy the GPL and make the MPL-covered source additionally available under GPL terms. This would change the product distribution terms, even if MPL notices stay on the source files; it is a fallback requiring owner choice, not the selected release path. [mpv's copyright file](https://github.com/mpv-player/mpv/blob/master/Copyright) and [FFmpeg's legal checklist](https://ffmpeg.org/legal.html) require an exact linked-component audit rather than relying only on build flags.

The preferred Windows path is a reproducible LGPL-eligible libmpv runtime with pinned component sources, build flags, hashes, complete notices, and corresponding source delivered with the release. [zhongfly's Windows builder](https://github.com/zhongfly/mpv-winbuild) publishes an LGPL-labeled libmpv variant, but its maintainer expressly does not guarantee that every incompatible component has been removed. It can be assessed as a candidate; its label alone is not release proof. The current OneAnime-matching DLL remains test-only until its exact component terms can be established. The source/build work must stay outside this repository's tracked third-party tree, consistent with the owner's no-clone/no-vendor instruction.

The current first-party loader verifies only the exact bundled DLL hash. [LGPL 2.1 Section 6b](https://www.gnu.org/licenses/old-licenses/lgpl-2.1.en.html) describes a suitable shared-library mechanism as one that works with an interface-compatible user-installed modification. Before selecting that compliance route, keep strict verification of the shipped DLL by default but provide and test a deliberate, documented way for users to run a compatible replacement, or establish a different Section 6 compliance route with appropriate source/relink materials. Do not silently accept a DLL from the search path. After the exact runtime is selected, rerun clean-host ZIP, actual playback and matched resource gates because a different build may change behavior and memory use.

The local implementation now accepts an explicit absolute DLL path and user-supplied SHA-256 through a pair of environment variables, while the default still verifies the bundled runtime pin. The existing loader applies the same regular-file, reparse-point, hash and held-handle checks to either path. Focused tests and an independent read-only review found no identified MUST_FIX; the final release still requires actual replacement-DLL operation and clean-host verification.

A bounded assessment of [zhongfly's 2026-09-25 LGPL-labeled x86-64 asset](https://github.com/zhongfly/mpv-winbuild/releases/tag/2026-09-25-35af06172b) verified archive SHA-256 `f86c2c942fa911aa0c6bc678fe5d17ae8e66e0f2aa17f8db88a03907c77ca498` against GitHub release metadata. Its archive contains only a 100,410,880-byte `libmpv-2.dll`, headers and an import archive: no license texts, component manifest or corresponding sources. Its DLL has a static `vulkan-1.dll` import, but the archive does not include that loader. This candidate does not satisfy the current clean-host portable or license gates; no product pin change was made.

The [mpv project's development build](https://github.com/mpv-player/mpv/releases/tag/git-release) also publishes an x86-64 LGPL-labeled DLL. The 2026-09-26 asset from [successful build run 36252823533](https://github.com/mpv-player/mpv/actions/runs/36252823533) has archive SHA-256 `bec23048354e9d5fe04372ffdc16f2590c716d516198a09ef9b90416ce4130fc`, matching GitHub's asset digest. It contains `LICENSE.LGPL`, headers, two libbluray Java archives, the import library and a DLL with SHA-256 `30d54ef7303bafc843587bee209d5a043a7f6df71c91d27c0aaeb5356f8f32fb`. The DLL's static imports are Windows/API-set libraries, so it avoids the first candidate's Vulkan loader dependency. The release describes the build as LGPLv3 but expressly calls it an untested development build, not a stable release. The archive has no build-specific component inventory or corresponding source bundle. Its [fixed-commit build script](https://github.com/mpv-player/mpv/blob/a1bf4b6559d6e644b967c22d87232dc77c7dd442/ci/build-mingw64-full.sh) clones moving FFmpeg, LuaJIT, Windows metadata and subrandr sources, and uses an FFmpeg build container tagged `latest`; the run log identifies container digest `sha256:ff679f7298f4a927ea8705c7523e61919d0eb6b632a5db18b36d29ed1158f89e` and FFmpeg short revision `b227d1e`. This improves provenance over a third-party label but still does not prove the exact source, notices and redistribution obligations for every linked component. It also conflicts with the owner's no-third-party-clone rule as an unmodified build recipe. No product pin or CI change was made from this asset.

## Windows release pipeline slice, 2026-09-27

The Windows packaging CLI now requires a schema-1 provenance JSON and a corresponding-source ZIP in addition to the libmpv DLL and license notice. The JSON binds the executable-pinned DLL SHA-256 to the source ZIP SHA-256, names at least mpv and FFmpeg with revisions, licenses and source entries, and the packager checks that listed entries are safe, nonempty and readable. Both files are included in the portable ZIP. This is an integrity and completeness *structure* check; it cannot determine whether every statically linked component or its legal obligations was correctly identified. Independent review found no remaining material code defect in this scoped package gate, and focused tests include missing data, mismatched hashes, traversal and corrupt source payloads.

The Windows package script now generates full root and nested license text for modules actually linked into the production Go desktop, then passes that generated notice file to the packager. It requires the libmpv provenance manifest and source ZIP as explicit inputs. FLTK 1.4.5 and its Windows patch remain a separate corresponding-source obligation because go-fltk statically links FLTK and its bundled JPEG, PNG and zlib. The generated Go notices include go-fltk's FLTK license text but do not themselves supply the modified FLTK source archive.

With the owner's authorization for a limited local CI change, a manually dispatched build probe was added. It downloads checksum-pinned mpv and FFmpeg source archives into the runner's temporary directory, uses a digest-pinned LGPL-labeled cross-build image, then disables container networking and source-wrap downloads. It uploads the resulting DLL, build configurations and input archives for inspection. An independent verifier/security review found no remaining execution or no-clone defect in the probe. It has not run in isolated CI, does not replace the executable's current OneAnime-derived DLL pin, and does not produce the full linked-component license/source manifest. Its output is diagnostic, not release evidence. Before enabling it as a PR/push release gate, complete the image dependency/source audit or replace the image with a fully archived build closure; then bind the selected DLL to the application pin and repeat native portable, playback and matched-resource acceptance.
