## Scope and hypothesis

Test one Windows vertical slice using the existing Go core, `pwiecz/go-fltk` for the desktop UI, and `gen2brain/go-mpv` with in-process libmpv. FLTK and libmpv are candidates, not proven lower-memory replacements. Keep the source, store, security, cancellation and playback ports; isolate native bindings behind narrow adapters. Build the slice in a repo-local `experiments/` directory with its own module if needed. Do not clone or vendor a third-party repository, change the production wiring, edit workflows, commit, push, or install tools globally as part of the prototype. The Windows-first product sequence remains; Linux and macOS runtime acceptance follows only if the Windows architecture passes.

The experiment must represent the real workload: six-section navigation, representative Home data and covers, visible focus, Tab/Shift+Tab, arrows, Enter/Space and mouse, one fixed 1080p clip started from the app, stop, episode switch, and repeated open/close. A blank window or direct standalone MPV launch cannot pass the slice.

## Controllable resource ownership

| Owner | First prototype policy | Evidence |
| --- | --- | --- |
| Home UI | Create only visible rows plus bounded prefetch; cancel reads and destroy offscreen widgets on leave. | Count live rows/widgets, outstanding reads, rebuild latency. |
| Covers | Bound decoded dimensions, concurrent decodes and cache bytes; release evicted native images explicitly. Start with an 8 MiB decoded-cover budget and tune only from measured quality and cost. | Track cache bytes, decode count, native image destruction and scroll responsiveness. |
| Network/data | Bound concurrent requests and response bytes; use cached state first; pause optional prefetch when inactive. | In-flight count, bytes, cancellation and idle CPU. |
| Player | Do not create libmpv before Play. Set bounded demuxer cache/readahead and decoder queues for the test clip; explicitly destroy the render context and player on Stop/Close. | Player/context lifetime, seek stability, audio/video quality, CPU/GPU and post-stop counters. |
| Whole process | Sample private working set, private commit, GPU allocation, CPU, page faults and responsiveness at each transition. Refuse optional work when its owner budget is exhausted; fail the experiment if the process envelope is missed. | Time series and peak/steady-state results, not one trimmed minimum. |

The 8 MiB cover value is an initial engineering budget, not an accepted product threshold. Go's runtime memory limit is soft and excludes native allocations; mpv's cache settings do not cap decoded frames, GPU surfaces or total process memory. Do not use forced GC, working-set trimming, intentional UI freezing, disabled security behavior or an OS hard-kill limit to fabricate a pass. If a bound causes buffering, broken controls or slow refocus, the slice fails rather than weakening user-visible behavior. Sources: [Go GC guide](https://go.dev/doc/gc-guide), [mpv manual](https://mpv.io/manual/stable/), [libmpv render API](https://github.com/mpv-player/mpv/blob/master/include/mpv/render.h).

## Ordered gates and stop rules

1. **Headless floor.** Run the existing Go service with representative local data but no GUI/player. Capture resource counters and component allocations. If this floor leaves no plausible room below OneAnime, diagnose that component before any GUI rewrite.
2. **FLTK Home.** Implement the smallest full navigation/Home slice, including keyboard/mouse/focus and bounded covers. Compare it with the existing Fyne build using identical data. Stop if the measured whole-process cost has no credible path below OneAnime; do not continue just because it beats Fyne.
3. **Embedded playback.** Add one libmpv session via the existing Player port. Verify render thread and input handoff, playback, episode switch, stop/cleanup, error paths and security boundary. Compare in-process and external MPV with the same MPV version, clip and decoder settings. Stop on persistent leaks, broken lifecycle or no resource advantage sufficient for the owner target.
4. **Reference comparison.** Only a functional candidate proceeds to a matched OneAnime run on the same owner-approved Windows host. Use the same counters for both products; record content, decoder, display scale and window state. Compare private resident with private resident, private commit with private commit, and whole-product playback with whole-product playback. These counters overlap and must not be added together. Report each run and variance; neither a single short sample nor a working-set minimum establishes PASS.

Initial screening can use short runs. The owner stopped the earlier 15-minute idle run and has **not** authorized a repeat; obtain fresh consent before any new long-idle sequence. Existing observations are in [Loop 28 evidence](LOOP28_M4_CONTRACT.md): Fyne app 169.50 MiB resident/304.97 MiB commit at 15 minutes minimized; separately launched app plus MPV 345.64 MiB resident/613.86 MiB commit at 30 seconds playback. That playback sample is not app-initiated or matched against OneAnime.

Success for this prototype means a functional, reviewable Windows slice with measured headroom below OneAnime across comparable Home and playback states and no broken security, keyboard/mouse or player lifecycle contract. Failure means stop with the exact measurement and component cause; it does not authorize raising the limit or silently changing the final UI/player. Passing the prototype does not complete Loop 28, Windows release or Linux/macOS acceptance.
