## Resource reference and measurement protocol

M0 defines the method; it performs no long-idle run. The M4 run requires the owner's fresh consent for the long-idle sequence and an agreed Windows reference host, fixed clip, representative profile, allowed variance and target interpretation. The provisional Windows targets in `PERF-008` are below 100 MiB sustained app-only idle private resident and below 250 MiB sustained combined app-plus-external-MPV playback private resident, with near-zero idle CPU and no monotonic cycle growth. These are not currently met or measured for the integrated app.

Use a release build and record commit/version, OS build, CPU/RAM/GPU, display scale, power mode, MPV version/decoder, profile and clip hashes, window dimensions/state, ambient load and measurement tool version. Construct a deterministic local profile containing 200 anime, 40 followed items, 20 history entries (including completed, duplicate and at least six distinct resumable anime), and 40 bounded cover images with recorded byte/dimension distribution. Keep the same six visible Home continuation rows and following preview when comparing builds; covers are loaded only by screens that actually request them. Use an approved, fixed local 60-second 1920×1080 H.264/AAC clip at 24 fps with recorded SHA-256, encoder settings and decoder mode; remote streaming and decoder changes are separate scenarios. The fixture generator and its manifest become M1/M2 verifier assets before integrated measurement. OneAnime cannot be called matched if its visible data or embedded player differs; label those comparisons observational only.

For each condition collect at least three independent runs and publish every sample plus median and range. Measure cold and warm startup, 10-second settle, 30-second foreground idle, Home scroll and typed Search action separately, ten open/close cycles, ten episode switches, sustained playback, stop/cleanup, and responsiveness. A full Search-screen interaction belongs to Loop 29 and is not an M4 migration prerequisite. Only after fresh consent add foreground → unfocused → specified long idle → focus/wake → playback → stop with identical timing on the same reference host. Sample at fixed intervals and transitions. Record private resident (`Working Set - Private` on Windows), private commit (`Private Bytes`), total process-tree commit and resident with shared-page caveat, incremental system memory against a same-host baseline, CPU time/rate and energy if available, GPU dedicated/shared allocation, page faults, disk I/O and startup/wake latency. Validate PID and descendants for every sample; report app-only, MPV-only and combined playback. On Linux/macOS collect the closest native resident/commit counters with precise definitions and platform-specific thresholds, not Windows counter names copied across OSes.

Interpret resident and commit together: lower resident with stable private commit and extra page faults can be OS trimming, while lower commit, stable wake latency and low CPU support actual sustained allocation reduction. Inspect Go heap/alloc profiles, Fyne widget/image retention and MPV process state before optimizing. Bound any optimization to an identified cause and measure its CPU/wake tradeoff. Do not force GC or trim a working set to manufacture a low minimum. If the agreed envelope still fails after bounded causal work, stop with measured evidence for an owner decision; never reinstate WebView or lower a gate silently.

## Portable state and legacy import contract for M3

The release archive extracts into a user-chosen folder. Resolve its installation root from the executable path, never the current working directory. Windows and Linux place the binary at that root; macOS places `AnimePortable.app` at that root and resolves the root as the bundle's parent. App-owned SQLite, settings and bounded cache live under `<root>/data/`; the primary database is `<root>/data/animeportable.db`. On macOS this is outside the signed `.app` bundle. MPV stays externally installed and its configured path is a setting, not a bundled copy. Moving the whole extracted folder with its `data/` preserves state; moving only the binary or `.app` does not.

Startup validates the resolved root and data directory, rejects remote/device paths and symlink redirection at sensitive file boundaries, and checks actual write/open ability before allowing a fresh database or mutation. A read-only folder produces a clear user-visible error with the required action (move/extract to a writable folder) and never falls back silently to AppData or a hidden system profile. It does not silently start an empty profile when an existing portable database is unreadable, malformed or incompatible. Existing SQLite path permissions, no-follow behavior, WAL artifacts, migrations and sanitized errors remain required; the M3 path layer must test parent-directory links and macOS bundle resolution explicitly.

Legacy source is the current `os.UserConfigDir()/AnimePortable/animeportable.db`. On first portable launch, the UI may offer a clearly labeled one-time **Copy existing data** choice only when this source exists and the portable target has no user data. The default choice creates an empty portable profile. Import is explicit, occurs before the portable database is opened for normal use, and never deletes, moves, renames or writes the legacy profile. A read-only consistent SQLite snapshot (including committed WAL data) is staged inside `<root>/data/`, validated with integrity/schema/version checks, then atomically installed with exclusive no-clobber semantics only if the destination is still empty; a check followed by a normal rename is insufficient. Never copy just the live `.db` file or overwrite an existing portable database. If snapshot, validation, permission or final install fails, preserve the legacy source and any previously valid portable target; remove only staging files created by that import after their paths are verified. Report a safe error and allow retry, empty-profile creation or exit. Imported records retain canonical IDs, following/history/progress/settings; source credentials and external MPV paths remain subject to current validation. No automatic merge is promised.

M3 tests must cover fresh extraction, repeated launch and in-place binary upgrade, moving the complete folder, read-only root/data directory, paths containing spaces and non-ASCII characters, absent/invalid MPV, legacy source with active WAL, corrupt/incompatible source, interrupted import, existing portable target, concurrent first-launch/import attempts and a symlinked path. Tests must assert the old profile's bytes remain unchanged and no state appears outside the chosen portable root. Windows, Linux and macOS must each run an extracted artifact without installer or privileged registration; document unavoidable OS runtime libraries separately.
