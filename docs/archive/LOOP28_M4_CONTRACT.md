## Focus-aware suspension slice

The owner directed a phased idle policy after reviewing the memory evidence. Fyne 2.8.1 exposes `App.Lifecycle().SetOnEnteredForeground/SetOnExitedForeground`; the GLFW driver calls them on focus changes. The current Home creates three cancellable reads and releases them when the view closes. The backend owns SQLite, HTTP clients and external MPV separately; its `Close` is terminal and cannot be used for reversible background suspension. MPV itself moves focus away from the Fyne window, so playback startup, active session, progress checkpoints and cleanup must remain independent of the Home UI.

Success for the smallest complete slice: a short focus loss does not churn the UI; a sustained loss cancels only Home reads and drops the Home widget tree after any pending Play start finishes, while leaving backend and external MPV untouched; returning focus restores the selected section, visible keyboard focus and asynchronous Home data without duplicated/stale callbacks. Closing the window still cancels everything and does not leak timers. Deterministic tests must cover delayed/suppressed suspend, pending Play, repeated loss/return, cancellation and close. Recheck Windows native behavior and resource counters after a code-reviewed implementation; the earlier 15-minute diagnostic must not be repeated without renewed owner direction. No resource PASS is inferred from an implementation alone.

The uncommitted implementation now uses Fyne foreground lifecycle callbacks, waits 30 seconds, cancels Home reads and replaces the Home tree with a small placeholder. It rebuilds the selected section on return without resizing the owner's window. Final-state focused/controller tests, full `go test -count=1 ./...`, native/backend race tests and `go vet ./...` pass locally. Independent quality/security reviews found a window-size regression and a forced-GC violation; the size regression was fixed with a test and the forced-GC call was removed. No remaining MUST_FIX was reported. Native owner-visible behavior and isolated final-state CI are not yet verified.

Two bounded same-host Windows diagnostic runs used the same representative fixture and 10-second foreground, 5/40/80-second minimized, and 5-second restored checkpoints. They are host diagnostics, not `docs/13` PASS evidence. The first run used the foreground teardown. The second was an experimental forced-GC build that independent review rejected under `docs/16`; that call was removed from the product code. The scripts and CSVs remain under `.slim/`.

| Run | Foreground 10s resident / commit | Minimized 80s resident / commit | Restored 5s resident / commit |
| --- | ---: | ---: | ---: |
| Teardown only | 177.77 / 325.88 MiB | 178.15 / 317.02 MiB | 189.17 / 336.48 MiB |
| Teardown plus `debug.FreeOSMemory` | 177.86 / 329.96 MiB | 167.98 / 300.76 MiB | 183.80 / 329.04 MiB |

The experimental GC build reduced both private resident and private commit, but idle remained about 68 MiB above the under-100 MiB gate and forced GC conflicts with the agreed sustained-allocation criterion. The retained product implementation's 80-second minimized sample was 178.15 MiB resident and 317.02 MiB commit. Fyne 2.8.1's local source keeps renderer/canvas caches during a minimized window's no-repaint loop: `glfw/loop.go` calls `cache.Clean(refreshed)`, and `cache/base.go` only destroys expired renderer/canvas entries when `refreshed` is true. This is a source-based explanation for retained UI allocations, not proof of exact byte ownership. No supported public Fyne API was found to clear those caches while preserving a focusable window. The bounded optimization has therefore not met the resource envelope; further implementation, resource verification and Loop 28 PASS are on hold pending an owner decision.

On 2026-09-25 the owner floated combined playback at or below 280 MiB as a compromise, then clarified that OneAnime can peak near 350 MiB while idling near 46 MiB and that AnimePortable must be genuinely low across states. No replacement numeric envelope was agreed, so `PERF-008` is unchanged. One short host diagnostic with the final no-forced-GC build, the representative 200-anime fixture, MPV 0.41.0 `--no-config --hwdec=no`, and the fixed 1080p60 clip measured 30-second playback at 176.76 MiB app plus 168.88 MiB MPV = 345.64 MiB combined private resident; combined private commit was 613.86 MiB. The MPV process was launched separately by the diagnostic script, so this run is a preliminary bound and cannot verify app-initiated playback, repeatability, GPU allocation or the final resource gate. CSV: `.slim/windows-resource-fixture-20260924/long-20260925T073118Z.csv`.

## OneAnime 1.4.7 focused source audit

The owner requested a deeper explanation before choosing another resource threshold. Read-only GitHub API inspection of tag `1.4.7` at [`cd92c9c74214aae0fca453cc268e005a29848888`](https://github.com/Predidit/oneAnime/commit/cd92c9c74214aae0fca453cc268e005a29848888) found no desktop focus/minimize policy that suspends all functions. [`windows/runner/win32_window.cpp`](https://github.com/Predidit/oneAnime/blob/cd92c9c74214aae0fca453cc268e005a29848888/windows/runner/win32_window.cpp) forwards `WM_ACTIVATE` to child focus; [`lib/pages/video/video_page.dart`](https://github.com/Predidit/oneAnime/blob/cd92c9c74214aae0fca453cc268e005a29848888/lib/pages/video/video_page.dart) clears danmaku on Windows restore, while its app `paused` handler is documented for Android/iOS. The popular page even requests keep-alive. This does not prove whole-repository absence, but the inspected lifecycle paths do not support the proposed all-function sleep explanation.

The source does implement narrower resource controls: [`popular_controller.dart`](https://github.com/Predidit/oneAnime/blob/cd92c9c74214aae0fca453cc268e005a29848888/lib/pages/popular/popular_controller.dart) starts from stored data and adds 20 items per scroll batch, while [`popular_page.dart`](https://github.com/Predidit/oneAnime/blob/cd92c9c74214aae0fca453cc268e005a29848888/lib/pages/popular/popular_page.dart) uses a lazy `ListView.separated`; [`player_controller.dart`](https://github.com/Predidit/oneAnime/blob/cd92c9c74214aae0fca453cc268e005a29848888/lib/pages/player/player_controller.dart) creates a media-kit player for the video page, sets a 15 MiB player buffer and disk demuxer cache, and disposes the player on page exit; the video page cancels its one-second timer on exit. The pinned [media-kit native library loader](https://github.com/Predidit/media-kit/blob/994465d9bfca3f39d0b41199d16e7fd93fe97881/media_kit/lib/src/player/native/core/native_library.dart) loads libmpv in-process, whereas AnimePortable's user-installed MPV is a separate process. Home already caps displayed history/following entries at six and does not start MPV, so copying those two patterns has no demonstrated path to the current idle gap. The OneAnime 15 MiB buffer is not a total-memory cap and the two players need matched decoder/cache/GPU settings for a useful playback comparison.

The owner's older OneAnime screenshots showed private resident falling from 94,688 to 27,276 KiB while private bytes rose from 303,180 to 307,524 KiB. This is consistent with Windows working-set trimming, not evidence that the app deallocated about 67 MiB. [Microsoft's working-set guidance](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/wpa-reference-set) confirms that working set is a momentary, OS-trim-sensitive measure. Flutter is not shown to be uniquely capable of a low idle reading, and OneAnime's exact 46 MiB observation cannot be explained from source alone. No third-party repository was cloned or copied into this workspace.

A separate 15-second Windows host diagnostic built with a temporary, removed `memoryprobe` build tag sampled the representative AnimePortable Home without forced GC: 175.98 MiB private resident, 325.95 MiB private commit, `runtime.MemStats.HeapAlloc` 87.72 MiB and `Sys` 102.79 MiB. The Go runtime's `Sys` is address space obtained from the OS, not an exact committed-memory partition; this snapshot suggests much of process commit lies outside Go runtime accounting but does not identify which native subsystem owns it. Trace: `.slim/windows-resource-fixture-20260924/go-gctrace-20260925T074707Z.txt`. [Go's GC guide](https://go.dev/doc/gc-guide) says runtime memory limits exclude C allocations and warns that baking a tight memory limit into a desktop application can hurt responsiveness. The next diagnostic target is component ownership, not GC tuning or forced trimming.

## Owner resource decision, 2026-09-25

The owner clarified that the whole AnimePortable experience must consume less resource than OneAnime in comparable states; a result that cannot meet that condition is a failure. The current Fyne build already fails the existing absolute idle criterion: 169.50 MiB private resident after the owner-stopped 15-minute run versus the under-100 MiB limit. Its preliminary app-plus-separately-launched-MPV sample was 345.64 MiB resident during fixed-clip playback; this is not a matched OneAnime benchmark or actual app-initiated playback. The owner's OneAnime 46 MiB idle and roughly 350 MiB peak are observations under different conditions, so no exact cross-product delta or universal impossibility claim is justified. Still, the current Fyne implementation cannot be called successful under the owner's necessary condition. A UI architecture decision is required before further migration work. [Proposed ADR-022](17_ADR_UI_RESOURCE_DECISION_PROPOSAL.md) records the options without changing the selected UI.
