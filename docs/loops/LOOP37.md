# Loop 37: Settings

Status: PASS (owner accepted 2026-10-22, owner check 5). Commits f582da8, 1966449 (CI crash fix), f2c4f51 (test wait under race); GitHub Windows CI 39734539484 green.

## Goal

A 設定 page where the user changes appearance, 自動下一集, 自動播放 and resume playback (language moved to Loop 37b). Each setting changes the app's behavior, is saved in the portable data folder (SQLite `settings` row), and is still set after the app restarts. No account and no telemetry.

Owner check (roadmap): change each setting, restart, and see each one kept.

## Owner decisions (2026-10-22)

- A. Theme: remove the theme button from the top right of Home. Theme lives only in the 設定 page, as a toggle. The exact control is an open question (the roadmap lists System, Light, Dark; one toggle cannot show three states). Keyboard access and visible focus follow the Loop 34 key policy.
- B. Autoplay becomes two independent settings:
  - 自動下一集: when an episode ends normally, load the next ordered episode in the same player (Loop 36 behavior).
  - 自動播放: a loaded episode starts playing at once instead of waiting paused.
  - Both on: the next episode loads and plays (full Loop 36 behavior). 自動下一集 on, 自動播放 off: the next episode loads and waits paused at its start. 自動下一集 off: playback stops at the end.
  - The on/off decision stays in one place (`autoplayEnabled` in `apps/desktop/player_autoplay.go`), extended for both settings. The stored `AutoplayNext` value is kept so current users keep their behavior.
  - The roadmap's Loop 37 in-scope line lists both settings (owner-approved scope change).
- C. Language: 繁體中文, 日本語 and English. If Japanese is costly, 繁體中文 and English are enough. Traditional Chinese stays the default; no Simplified Chinese anywhere.

## Current behavior (inventory 2026-10-22)

- Storage: `core.Settings` (`core/models.go`) has `Appearance` (System, Light, Dark), `AutoplayNext`, `ResumePlayback` and `Language` (Traditional Chinese, English), each with an Unspecified zero value. SQLite keeps one row (`settings`, id 1); the CHECK constraints come from migration 0003. `DefaultSettings` sets only `AutoplayNext` to enabled. The backend already exposes `Settings` and `SaveSettings`; no new backend action is needed.
- Missing in storage: a column for 自動播放, and a Japanese language value (`language IN (0, 1, 2)`). Both need a new migration (0007, a table rebuild like 0003). The migration-count tests (`episode_mappings_test.go`, `schedule_test.go`) then expect 7.
- Theme: a button in the Home header (`fltkhome/window_windows.go`) flips light/dark and saves `Appearance` through an async writer (`fltkhome/appearance.go`) that reads the stored settings and rewrites them. Anything but dark loads as light; nothing reads the Windows app theme, so "System" does not work. Default is light.
- Autoplay: `autoplayEnabled` reads `AutoplayNext` (default enabled) when an episode ends. No screen changes it. libmpv is never told to pause, so every loaded episode plays at once.
- Resume: `playbackResumePosition` (`core/app.go`) uses the saved position only when `ResumePlayback` is enabled, and it is Unspecified (off) for every install, because no screen sets it. So 播放 on the detail page, choosing an episode in the player and autoplay all start from 0. The 繼續觀看 / 繼續播放 buttons (Home, detail, 歷史紀錄) send an explicit position and ignore the setting.
- Language: no translation layer. About 200-250 Traditional Chinese literals in `apps/desktop` (largest: Home window, search, Home model, following, detail, schedule, history) plus 4 in the player overlay (C++). Buttons have fixed widths (for example nav 177 px), so English and Japanese labels need a layout check. Bangumi text is converted with s2twp at the adapter; titles and synopses are content, not UI text.
- Navigation: 設定 already exists in the left nav (Home) and the player menu and shows 此頁面尚未建立. The Settings page goes there.

## Gaps

1. No 設定 page exists. It needs keyboard access (Tab order, Enter/Space to toggle) and a visible focus ring in light and dark.
2. Theme: the Home header button must be removed. The System option has no code: it needs a read of `AppsUseLightTheme` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize` (read only).
3. 自動播放 has no stored field and the engine cannot load an episode paused; both are needed.
4. Resume playback has no control, and its default and which buttons it affects are undecided (open question 3).
5. Language has no string table. Every UI literal must move into one, with English (and Japanese) text, a check that translated labels fit their fixed-width buttons, and a check that the UI font shows Japanese kana.
6. Two writers would share the settings row: the theme writer in `fltkhome/appearance.go` reads, changes and rewrites the whole row, so it could overwrite a save from the 設定 page. Saves must go through one writer.

## Owner answers (2026-10-22)

1. Theme: a 跟隨系統 toggle plus a 深色 toggle that is disabled while 跟隨系統 is on (keeps System, Light, Dark). A new install follows the system.
2. 自動播放 applies only to the episode that 自動下一集 loads. Any episode the user opens by hand (播放 on the detail page, 繼續觀看, 歷史紀錄, the player's episode list) plays at once. 自動播放 is on by default, so current behavior is kept.
3. Resume playback is on by default. When on, 播放 on the detail page, the player's episode list and 自動下一集 start at the saved position (finished or nearly finished episodes start at 0, as today). When off, they start at 0; the 繼續觀看 / 繼續播放 buttons still resume, because resuming is what they are for.
4. Language moves to a separate Loop 37b with 繁體中文, English and 日本語 (roadmap updated).

## Scope

In scope:

- Core owns the defaults: one function resolves a stored value of Unspecified to its default (appearance System, 自動下一集 on, 自動播放 on, resume on). Every reader uses the resolved settings; no screen has its own default.
- Storage: migration 0007 adds an `auto_play` column (Toggle, CHECK 0-2, default 0 = Unspecified, which resolves to on). The stored `autoplay_next` value is not touched, so a user who turned 自動下一集 off keeps it off. The migration-count tests move from 6 to 7. `core.Settings` gains `AutoPlay`; the backend DTO gains `autoPlay` (same `Settings` / `SaveSettings` actions, no new backend action).
- 設定 page in the existing nav slot (index 5, Home and the player menu), rows in this order: 主題 as one segmented control 跟隨系統 | 暗色 | 明亮 (owner check 1), then the toggles 自動下一集, 自動播放 (disabled while 自動下一集 is off), 從上次位置繼續播放. Each change saves at once. Tab / Shift+Tab and Up/Down move between rows (主題 is one stop), Left/Right move between the 主題 segments (Left on the first goes to the navigation), Enter and Space select or toggle, Esc goes back (Loop 34 key policy). The focused segment or toggle shows a visible focus ring in light and dark, also on the selected segment; the selected segment is marked by a check and bold text, not by colour alone.
- Theme: the Home header button and its tooltip are removed. 跟隨系統 reads `AppsUseLightTheme` (HKCU, read only) at startup and when 跟隨系統 is chosen; if the value is missing or unreadable the app uses light. A Windows theme change while the app runs takes effect at the next start.
- One settings writer in the UI replaces the theme-only writer (`fltkhome/appearance.go`): it saves the whole settings value the UI holds, coalesced and in order, so a theme save and another toggle never overwrite each other. Save and load failures keep the current messages, reworded from 主題設定 to 設定.
- Autoplay: `playerAutoplay` keeps one decision point. At a normal end it reads the settings once: 自動下一集 off stops cleanly (Loop 36); on loads the next episode; 自動播放 decides whether that load plays or waits paused at its start position. The engine gains a paused load (mpv `pause` set for that load only); manual loads always play.
- Resume: `playbackResumePosition` (core) is unchanged except that it reads the resolved setting, so Unspecified now resumes.

Out of scope: language (Loop 37b), aspect ratio, low-memory mode, a player-path setting, live reaction to a Windows theme change.

A change applies to new connections without a restart. The Windows system proxy is read from HKCU WinINet settings (read only); if it is off or unreadable, no proxy is used.
- 檢查更新: a button that asks the GitHub API for the releases of `loustack17/AnimePortable` (pre-releases included, drafts ignored) and compares the newest with the version constant in `internal/release` (`0.2.0-alpha` until the next release; 05_WORKFLOW section 11 now bumps it). It shows 已是最新版本（v…） or 有新版本 v… with 開啟下載頁, which opens that GitHub release page in the default browser. It never downloads or runs anything and never checks on its own.
- 資料位置: the 設定 page shows the current data folder, 變更位置… (a folder picker) and 恢復預設位置.
  - Changing copies the open database into the chosen folder as one consistent snapshot (SQLite `VACUUM INTO`), checks the copy opens, then writes `data-location.txt` next to the exe (one absolute path; the database cannot hold its own location). It shows 重新開啟程式後生效. The old data stays where it was.
  - If the chosen folder already has `animeportable.db`, the user picks 使用該資料夾的資料 or 以目前資料覆蓋; overwriting renames the old file to `animeportable.db.bak-<timestamp>` first, nothing is deleted.
  - 恢復預設位置 works like a change to the `data` folder next to the exe, then removes `data-location.txt`.
  - The chosen path passes the same checks as the default (absolute, local, no UNC or device paths, no links). At startup, if the chosen folder or its database is missing, the app says so and asks 使用預設位置 or 結束; it never starts an empty second copy silently. `playback-failures.log` follows the database.
- New backend actions (owner-approved features): `CheckForUpdate`, `TestProxy`, `DataLocation` and `MoveDataLocation`; the `main_test.go` allowlist gains exactly these four. The data-folder moves need the open store, which only the Service holds, so they are Service actions over the `PortablePlan` / `LocationMove` logic; the startup check for a missing folder stays on `PortablePlan`.
